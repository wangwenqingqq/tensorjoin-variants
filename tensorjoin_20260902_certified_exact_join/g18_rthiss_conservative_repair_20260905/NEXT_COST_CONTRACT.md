# Next complete-cost comparison: boundaries to freeze before implementation

Not a timed result or an admitted new campaign. G18's diagnostic counters,
raw masks, CPU validation and evidence IO explicitly disqualify its operational
wall time from a speed table. A low fallback fraction alone is not a speedup.

## Public operation

Immutable contiguous host FP32 input plus the declared stored threshold -> all
canonical sorted original host uint64 pair IDs, inclusive directed/self policy.
The first screen must use the same G2A4096x512 input and pair oracle for every
participant; no ratio against G16's old60K observation. Keep G16 and the complete
pedantic FP32-first control unchanged until any shape-specific routing is
inspected and frozen. Warm up and remeasure every admitted participant together.

The next adapter must charge every required input clone, dimension/point reorder,
cutoff construction/configuration, H2D allocation/transfer, candidate construction,
refinement/fallback, compaction/count readback, D2H metadata/output and canonical
sort. File decoding, oracle generation and post-timer validation can be excluded
only identically across participants, with live output consumption inside scope.
No hidden precomputed pairs, masks, reordered data or candidate lists.

## Engine lifecycle is a fairness gate

RT-HiSS's current main creates an OWL context/program pipeline for one operation;
it is not a proven reusable-operator API. TensorJoin/cuBLAS already have warmed
library/JIT state in their in-process tests. Do not quietly compare fresh RT
engine construction to a cached TensorJoin engine and label that the strongest
steady-state baseline. Conversely, do not subtract RT setup from a fresh-call
number after observing it.

Separate and freeze reusable-engine versus fresh-invocation contracts. If a
reusable RT wrapper is implemented, retain upstream algorithms but audit every
resource owner, destruction/reset, pointer lifetime and mutable global. Simply
calling main repeatedly is unsafe: threshold/global counters, static timings,
OWL objects and CUDA buffers need explicit lifecycle evidence. Admit sanitizer,
repeat and memory-stability gates for that exact new wrapper before its timing.
If this cannot be supplied, report the narrower lifecycle honestly and retain
the modern steady-state comparator gap rather than overclaiming superiority.

## Normalizing diagnostics without changing the algorithm

A separate build may disable G18 diagnostic atomics/raw mask capture and disk
exports. Keep conservative thresholds, FP64 terminal, original-ID recovery,
complete output materialization and validation invariants. Inspect the actual
runtime-selected instruction stream and resources: diagnostic-on safety is not
automatically diagnostic-off safety. Compare complete pair hashes on all G18
fixtures and pass new safety/repeat tests before timing.

Native-quality RT-HiSS is a separately labeled control, not interchangeable with
the repaired FP64-reference row. A full-FP64-all-candidate control can attribute
repair costs but must not become the sole external baseline. Broader or60K
inputs require fresh candidate-completeness, integer capacity and output checks.

## Predeclared performance decision

Choose the estimator, process count, alternating order and confidence/stopping
rules before observing latency. Keep every process and order split, including
unfavorable results. No profiler durations, excluded debug captures, favorable
single medians or incomparable shapes enter a headline ratio. Start with one
small fair screen; expensive multi-dataset/sustained campaigns still require
Gate0 and a defensible non-incremental thesis, not only engineering completion.
